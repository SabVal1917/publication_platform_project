### Тема проекта:

## **Платформа для публикации и обсуждения статей по программированию**

**Страницы на Сайте (Frontend):**

- Главная страница со списком статей
- Cтраница отдельной статьи с комментариями
- Cтраницы для создания/редактирования статей
- Страница профиля пользователя
- Страницы регистрации и входа

---

**API и Взаимодействие Пользователя с Сайтом:**

API предоставляет возможности:

- Регистрации, вход, просмотр/редактирование профиля
- Для статей функционал: получение списка, просмотр,
  создание, редактирование, удаление, лайки
- Для комментариев функционал: добавление, редактирование, удаление, лайки.
- Пользователь взаимодействует с сайтом через формы и кнопки, которые отправляют соответствующие запросы к API.

---

**Что Будем Хранить в БД:**

- **Пользователи** (ник, почта, пароль),
- **Статьи** (заголовок, содержимое, автор, дата, количество лайков/комментариев),
- **Комментарии** (содержимое, автор, к какой статье/комментарию относится),

## Сценарии использования (User Stories)

Проект представляет собой платформу для обмена знаниями. Ниже описаны основные сценарии взаимодействия пользователей с системой.

### 1. Сценарий «Читатель» (Гость)

- **Цель:** Найти решение технической проблемы или узнать что-то новое.
- **Поток:**
  1.  Пользователь заходит на **Главную страницу**. Видит список популярных статей, отсортированных по дате.
  2.  Кликает на заголовок статьи.
  3.  Попадает на **Страницу просмотра**, где отображается контент (`content`), автор (`author_id`) и счетчики активности.
  4.  Видит интересную дискуссию в комментариях. Чтобы принять участие, нажимает «Войти».

### 2. Сценарий «Автор»

- **Цель:** Опубликовать туториал или статью.
- **Поток:**
  1.  Авторизованный пользователь переходит в **Редактор статей**.
  2.  Заполняет заголовок. Система автоматически генерирует `slug` (человекопонятный URL), проверяя его на уникальность.
  3.  Пишет текст, использует Markdown-разметку, прикрепляет обложку.
  4.  Нажимает **«Опубликовать»**.
  5.  Статья сохраняется в БД, привязывается к его `id` и становится доступна всем пользователям.

### 3. Сценарий «Социальное взаимодействие»

- **Цель:** Оценить контент и обсудить его.
- **Поток (Лайки):** Пользователь нажимает кнопку "Лайк".
  - Если лайка не было: создается запись в таблице `article_likes`, счетчик `likes_count` в статье увеличивается на +1.
  - Если лайк был: запись удаляется, счетчик уменьшается на -1 (toggle-эффект).
- **Поток (Комментарии):** Пользователь пишет: _"Ты ошибся в строке 5!"_.
  - Автор статьи видит комментарий и нажимает **«Ответить»**.
  - Создается новый комментарий, у которого поле `parent_id` ссылается на комментарий читателя. Так формируется древовидная структура (ветка обсуждения).

## Взаимодействие сущностей и логика БД

В этом разделе описано, как технически реализована бизнес-логика на уровне базы данных.

### 1. Авторы и Контент (1:N)

- **Связь:** `users.id` ⟷ `articles.author_id`
- **Логика:** При создании статьи мы берем ID текущего залогиненного пользователя и записываем его в `author_id`. Это позволяет на странице профиля одним запросом (JOIN) получить все статьи конкретного человека.

### 2. Древовидные комментарии (Self-Reference)

- **Связь:** `comments.id` ⟷ `comments.parent_id`
- **Логика:** Таблица ссылается сама на себя.
  - Корневой комментарий к статье имеет `parent_id = NULL`.
  - Ответ на комментарий содержит `parent_id`, равный `id` родительского комментария.
  - Это позволяет строить вложенные дискуссии любой глубины.

### 3. Система Лайков (M:N)

- **Связь:** `users` ⟷ `article_likes` ⟷ `articles`
- **Логика:** Реализована через промежуточную таблицу (связующую сущность).
  - Это предотвращает накрутку: уникальный составной ключ (или проверка на уникальность пары `user_id` + `article_id`) гарантирует, что один пользователь может поставить только один лайк на одну статью.
  - **Оптимизация:** Чтобы при каждом просмотре статьи не считать количество строк в таблице `likes` (операция `COUNT(*)`), мы храним денормализованное поле `likes_count` прямо в таблице `articles` и обновляем его при добавлении/удалении лайка.

### 4. Уникальность данных

- Поля `email` и `username` в таблице `users` имеют ограничение **UNIQUE**, чтобы предотвратить дублирование аккаунтов.
- Поле `slug` в `articles` также уникально, так как оно используется в URL-адресе страницы (например, `site.com/articles/my-unique-post`).

## mermaid UML диаграмма

```erDiagram
    users {
        SERIAL id PK
        VARCHAR_50 username UK
        VARCHAR_100 email UK
        VARCHAR_255 password_hash
        VARCHAR_255 avatar_url
        TEXT bio
        TIMESTAMP created_at
        TIMESTAMP updated_at
    }

    articles {
        SERIAL id PK
        VARCHAR_200 title
        VARCHAR_200 slug UK
        TEXT content
        INT author_id FK
        INT likes_count
        INT comments_count
        TIMESTAMP created_at
        TIMESTAMP updated_at
    }

    comments {
        SERIAL id PK
        TEXT content
        INT author_id FK
        INT article_id FK
        INT parent_id FK
        INT likes_count
        TIMESTAMP created_at
        TIMESTAMP updated_at
    }

    article_likes {
        INT user_id PK_FK
        INT article_id PK_FK
        TIMESTAMP created_at
    }

    comment_likes {
        INT user_id PK_FK
        INT comment_id PK_FK
        TIMESTAMP created_at
    }

```

## Связи в проекте с красивым оформлением.

| Связь               | Тип        | Описание                           |
| ------------------- | ---------- | ---------------------------------- |
| users → articles    | 1:N        | Пользователь пишет много статей    |
| users → comments    | 1:N        | Пользователь пишет много комментов |
| articles → comments | 1:N        | Статья имеет много комментов       |
| comments → comments | 1:N (self) | Коммент может иметь ответы         |
| users ↔ articles    | M:N        | Лайки (через article_likes)        |
| users ↔ comments    | M:N        | Лайки (через comment_likes)        |
