# Отчёт

## Доменная область

Приложение является платформой для публикации и обсуждения статей по программированию.

Пользователь может:

- зарегистрироваться и войти;
- посмотреть список статей;
- открыть статью и комментарии;
- создать статью;
- изменить или удалить свою статью;
- оставить комментарий;
- поставить или убрать лайк.

Изменять и удалять чужие статьи нельзя. Для защищённых операций используется JWT-токен.

## Стек реализации

### Frontend

- React 19;
- React Router;
- React Hook Form;
- Parcel;
- nginx для раздачи файлов и проксирования запросов к API.

Frontend собирается командой npm run build. Parcel кладёт результат в каталог frontend/dist. Dockerfile сначала собирает проект в Node.js, затем копирует результат в образ nginx.

### Backend

- Go 1.27.0;
- роутер chi;
- pgx через database/sql;
- JWT для авторизации;
- bcrypt для хеширования паролей;
- Prometheus client для метрик;
- golang-migrate для миграций.

Backend предоставляет HTTP API на порту из переменной HTTP_PORT. По умолчанию используется порт 8080.

### База данных и инфраструктура

- PostgreSQL 15;
- Docker и Docker Compose;
- nginx;
- pgAdmin для локальной работы с базой;
- SQL-миграции с файлами up и down.

В docker-compose.yml описаны сервисы db, pgadmin, migrate, backend и frontend.

## Основные сущности

### Пользователь

Хранит имя, email, хеш пароля, аватар, описание профиля и даты создания и изменения.

### Статья

Хранит заголовок, slug, текст, автора, число лайков, число комментариев и даты создания и изменения. Slug является уникальным текстовым идентификатором статьи.

### Комментарий

Хранит текст, автора, статью, родительский комментарий, число лайков и даты создания и изменения. Родительский комментарий позволяет делать ответы на комментарии.

### Лайк статьи

Связывает пользователя и статью. Один пользователь может поставить одной статье только один лайк.

### Тег

Хранит название тега. Таблица article_tags связывает статьи и теги.

## Соответствие методологии 12 Factor App

### 1. Codebase

Статус: соответствует.

Frontend, backend, миграции и Docker-конфигурация находятся в одном Git-репозитории. У приложения одна кодовая база. Из неё можно создавать разные развёртывания с разными настройками.

### 2. Dependencies

Статус: соответствует.

Зависимости backend записаны в backend/go.mod и backend/go.sum. Зависимости frontend записаны в frontend/package.json и frontend/package-lock.json. Сборка выполняется в Docker и не зависит от случайно установленных пакетов на компьютере разработчика.

### 3. Config

Статус: частично соответствует.

Настройки HTTP-сервера, PostgreSQL, пула соединений и JWT передаются через переменные окружения. Пример находится в .env.example. Настоящий .env не добавляется в Git.

Ограничение: логин и пароль pgAdmin пока записаны прямо в docker-compose.yml. Для production их тоже нужно вынести в переменные окружения. Значения из .env.example подходят только для локального запуска.

### 4. Backing services

Статус: соответствует.

PostgreSQL рассматривается как внешний сервис. Адрес, порт, имя базы, пользователь, пароль и SSL-режим задаются через окружение. Backend не привязан к конкретному адресу базы данных.

### 5. Build, release, run

Статус: соответствует.

Сборка выполняется в Dockerfile. Backend компилируется в команды api и migrate. Frontend собирается Parcel и копируется в отдельный образ nginx.

Миграции выполняются отдельным одноразовым сервисом migrate. Backend запускается только после успешной миграции. Сборка, обновление схемы базы и запуск API разделены.

### 6. Processes

Статус: соответствует.

Backend не хранит пользовательские сессии в памяти и не записывает рабочие данные в локальные файлы. JWT передаётся клиентом, а постоянные данные находятся в PostgreSQL. Другой экземпляр backend может обработать следующий запрос того же пользователя.

### 7. Port binding

Статус: соответствует.

Backend сам запускает HTTP-сервер на порту из HTTP_PORT. Frontend обслуживается nginx на порту 80, который Docker Compose публикует как localhost:3000.

### 8. Concurrency

Статус: частично соответствует.

Go обрабатывает HTTP-запросы конкурентно. Размер пула PostgreSQL ограничен и настраивается через окружение. Изменение лайков и счётчиков выполняется атомарно в транзакциях.

Backend не хранит состояние и подходит для нескольких экземпляров с одним JWT_SECRET. Но в текущем Compose у backend задан фиксированный container_name. Поэтому обычное масштабирование командой docker compose up --scale backend=2 не сработает. Для Kubernetes понадобятся Deployment и Service, а фиксированное имя контейнера нужно убрать.

### 9. Disposability

Статус: соответствует.

Backend обрабатывает SIGINT и SIGTERM. Перед остановкой readiness-проба начинает возвращать ошибку. Затем сервер ждёт drain delay и завершает текущие HTTP-запросы с таймаутом. Если мягкое завершение не успело, соединения закрываются принудительно.

Такой порядок позволяет Kubernetes убрать pod из Service до завершения процесса.

### 10. Dev/prod parity

Статус: частично соответствует.

Локально основные части запускаются в контейнерах: nginx, backend, миграции и PostgreSQL. Версии образов и зависимости описаны в репозитории, поэтому окружение можно повторить.

Полного совпадения с production пока нет. Compose запускает по одному экземпляру сервисов, PostgreSQL не имеет репликации, а Kubernetes-манифестов ещё нет. pgAdmin является локальным инструментом и не нужен в production.

### 11. Logs

Статус: соответствует.

Backend пишет структурированные JSON-логи в stdout. В логах запросов есть метод, путь, статус, время выполнения и request ID. Ошибки health checks тоже логируются. nginx и процесс миграций пишут в stdout и stderr. Приложение не управляет файлами логов.

Сбор и хранение логов должны выполнять Docker, Kubernetes или отдельная система логирования.

### 12. Admin processes

Статус: соответствует.

Миграции вынесены из запуска API в отдельную команду migrate. Они используют тот же Docker-образ, зависимости и конфигурацию базы, что и backend. Миграции имеют версии и могут применяться повторно без изменения уже обновлённой схемы.

## Наблюдаемость и проверки

Backend предоставляет:

- /health/live для проверки работы процесса;
- /health/ready для проверки готовности и доступности PostgreSQL;
- /metrics для метрик Prometheus;
- JSON-логи HTTP-запросов в stdout.

В проекте есть unit-тесты и integration-тесты. Основные команды проверки:

    cd backend
    go test ./...
    go test -race ./...
    go vet ./...

Integration-тесты требуют PostgreSQL и запускаются отдельно с build tag integration.

## Запуск приложения

Нужно создать локальный .env из примера и запустить Compose:

    cp .env.example .env
    docker compose up --build -d
    docker compose ps

После запуска frontend доступен по адресу http://localhost:3000. Запросы /api проксируются nginx на сервис backend:8080.

Для остановки:

    docker compose down

Данные PostgreSQL остаются в Docker volume postgres_data. Команда docker compose down -v также удаляет локальные данные базы.
