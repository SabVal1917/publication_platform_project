# Отчёт: SLI, SLO, SLA и error budget

## Реализация

Переиспользованы HTTP-метрики приложения и VictoriaMetrics.

Графики: <http://localhost:8428/vmui/>.

Пробер - `backend/cmd/prober/main.go` запрашивает `/api/articles` каждые 5 секунд, проверяя backend и чтение из PostgreSQL.

Успех: HTTP 200 и получение всего ответа за 2 секунды.

Deployment: `k8s/sre/prober.yaml`. Сбор метрик через порт 8081 каждые 15 секунд.

## Метрики

| Метрика | Описание |
| --- | --- |
| `publication_platform_http_requests_total` | Счётчик запросов с labels `method`, `route`, `status` |
| `publication_platform_http_request_duration_seconds` | Гистограмма времени ответа; `_bucket{le="0.5"}` считает ответы до 500 мс, `_count` считает все наблюдения |
| `publication_platform_http_requests_in_flight` | Число запросов в обработке |
| `publication_platform_probe_success` | Результат последней пробы: 1 или 0 |

Первые три метрики существовали ранее. 

Пробер также экспортирует длительность
и время последней пробы. 

HTTP SLI учитывают `/api/.*`, кроме `/api/ping`.

Ответы 4xx, включая 404, исключены; 5xx считаются ошибками.
Счётчики рассчитываются через `sum(increase(...[окно]))` с учётом перезапусков.

## SLI, SLO и SLA

| SLI | Формула, % | SLO | SLA |
| --- | --- | --- | --- |
| Успешность HTTP, RBSLO | `100 * (1 - E / N)` | >=99,5% | >=99% |
| Быстрые успешные ответы, RBSLO | `100 * F / N` | >=95% | >=90% |
| Запас по нагрузке, TBSLO | `100 * G_load / M` | >=99% | Внутренняя цель |
| Доступность по проберу, TBSLO | `100 * G_probe / M` | >=99% | >=98% |

`N`: учитываемые запросы; `E`: ответы 5xx; `F`: ответы 2xx/3xx до 500 мс.
Для задержки используются `_bucket` и `_count`.
`M`: все минуты; `G_load`, `G_probe`: хорошие минуты.

Хорошая минута нагрузки: максимум <=10 запросов в обработке при одной реплике.
Хорошая минута пробера: все собранные значения `success=1`, последняя проба
не старше 30 секунд. Оба SLI требуют минимум четырёх успешных скрейпов за минуту.
Пропуски не считаются хорошими минутами.

Общее SLA выполняется при достижении трёх публичных порогов:

```text
SLA_OK = (HTTP >= 99%) && (быстрые ответы >= 90%) && (пробер >= 98%)
```

## Error budget

`q`: целевой SLO; `s`: фактический SLI, оба в долях от 0 до 1.
`T`: число запросов или минут.

```text
Допустимые плохие события = (1 - q) * T
Расход бюджета, % = 100 * (1 - s) / (1 - q)
Остаток бюджета, % = 100 - расход
Burn rate = (1 - s) / (1 - q)
```

Расход выше 100% означает превышение бюджета.
Запросы разделены на `demo` и `objective_30d`.
На графиках показаны SLI, постоянные линии SLO/SLA и расход бюджета.

## Изменения для тестирования

Демо-режим для `GET /api/articles` переключается через
`POST /internal/sre-demo/{mode}`. 

Код: `backend/cmd/api/sre_demo_enabled.go`.

Включается сборкой с тегом `sre_demo` через `GO_BUILD_TAGS` в Dockerfile.

В обычной сборке отсутствует. Ошибки и задержки учитываются прежними метриками.

Скрипт `scripts/sre-demo.sh` создаёт нагрузку: 12 работников,
пауза 0,2 секунды между запросами. 

Последовательность режимов:

| Режим | Время | Изменение графиков |
| --- | --- | --- |
| `normal` | 45 с | Обычный трафик, исходные значения SLI |
| `error` | 30 с | HTTP 500, снижение успешности и результата пробера, рост расхода бюджета |
| `slow` | 30 с | Задержка 800 мс, снижение доли быстрых ответов, рост p95 и запросов в обработке |
| `normal` | 60 с | Восстановление по мере обновления окон |

Перед записью выполняется прогрев, затем запускается демонстрация:

```bash
bash scripts/sre-demo.sh normal 180
bash scripts/sre-demo.sh demo
```

После завершения или прерывания скрипт возвращает режим `normal`.
Минутные SLI могут восстанавливаться позже последней успешной пробы.
